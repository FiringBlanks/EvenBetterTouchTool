# Native macOS volume indicator investigation — 2026-10-26

Apple documents volume adjustment through its keyboard, Sound menu, and audio APIs, but no supported display-only HUD API was found. The author of [MacHUD](https://github.com/orchetect/MacHUD) explicitly describes the absence of a public system-HUD API. The [original OSDUIHelper investigation](https://ffried.codes/2018/01/20/the-internals-of-the-macos-hud/) describes a private XPC interface. [MonitorControl’s current OSD implementation](https://github.com/MonitorControl/MonitorControl/blob/main/MonitorControl/Support/OSDUtils.swift) has special handling on macOS 26/27 for traditional OSDs, illustrating the compatibility distinction from Tahoe’s current native feedback.

On this Apple Silicon macOS 26.6.2 host, a standalone metadata probe loaded the private OSD.framework through dyld and found OSDManager, sharedManager, the filled/total display selector, and fadeClassicImageOnDisplay. A separate short probe invoked the display selector with the actual current output level (about 45%). It did not send volume keys, change audio, change preferences, or grant permissions. The call returned without an error; that does not prove that a HUD was displayed. Computer-use inspection of the system helper timed out, and the user reported no confirmed visible native indicator. The probe therefore did not establish native compatibility.

Version 2.5.2 keeps the owned nonactivating indicator. No private OSD code is included in the shipped application, and no silent best-effort option claims native success. Synthesizing volume keys solely to summon the HUD could alter the actual volume or override custom step sizes; no such workaround is used. Reliable native display and controlled early dismissal remain outstanding. Users can still open macOS’s Sound menu themselves; normal hardware volume keys retain their system behavior.
